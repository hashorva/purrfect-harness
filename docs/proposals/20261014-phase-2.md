# Phase 2 proposal — Yield per token <!-- markdownlint-disable MD025 -->

## 1. Why

Phase 1 made every run provable. Phase 2 makes the harness **useful per token**:
get the most accepted work from the owner's subscriptions, give small models the
first chance, and let the harness learn how to split work so small models succeed.

Two outside findings support this direction:

- _The ultimate guide to multi-harness RL_ (Hugging Face, Sept 2026): the
  harness changes results more than the model. The same weights solved 62% of
  tasks in one harness and 33% in another. "There is no best harness, only a
  best pairing." A small bonus for fewer tool calls, given only to correct
  answers, cut tool calls by 31%.
- Andrej Karpathy on output formats: controlled language (ASD-STE100) for text
  that models read, and diagrams or HTML for what humans review.

We cannot train vendor weights. Our "training" is in context: how the
Architect splits and writes tasks, which (model, door, effort) gets which task
class, and how verification scores the result. Missions are the rollouts. The
ledger holds the rewards.

## 2. Principles

1. **Credit small models first.** A pass by an economy model scores higher than
   the same pass by a premium model. Score = verified pass × (1 + small bonus for
   lower tier, fewer tokens, fewer turns). A failure scores 0.
2. **Facts are mechanical; judgment is scarce.** Scripts decide pass or fail
   (tests, linters, typecheck, anti-gaming). Models are called only for judgment.
3. **Incentives, not walls.** Hard rules stay only where a script enforces them
   cheaply. Everything else is a scored preference or a budget.
4. **Time is cheaper than money.** Prefer serial cheap attempts. Spend parallel
   or extra attempts on quota that would otherwise expire unused.
5. **Every outside idea is a hypothesis.** It enters with a metric and a trial.
   It is adopted only when the data shows a gain.
6. **Files are memory.** No state lives only in a chat.

Architect can be any vendor. Both must work from day one in Claude Code, Codex,

## 5. Routing rules

- **The routing unit is (model, door, effort).** A door is a CLI plus the
  subscription behind it. Opus through Claude, Antigravity or Cursor are three
  doors with different quota and different harness behavior.
- **Door priority per model.** Example: Opus → Claude, then Antigravity, then
  Cursor. A model with no included home door goes to a door where it is
  included (Fable → Cursor).
- **Pools.** Quota belongs to pools, not CLIs. `grok` and Grok-in-Cursor share
  one weekly pool. Composer and the other Cursor models use Cursor's included
  usage.
- **Billing class.** Each door is `included`, `credits` or `api`. Only
  `included` is automatic. `credits` and `api` need explicit mission approval.
- **No-ZDR flag.** Doors marked no zero data retention can be forbidden per
  project.
- **Fast modes are off** unless the owner enables them for a mission. A `-fast`
  model is never chosen automatically (already true in v3.0.0).
- **Latest model, automatically, never silently.** Seats name a family and a
  policy. Each spawn resolves the newest entitled model, records it in the
  spec, and records the observed model in the receipt. A change between runs is
  a logged drift event. This amends the Phase 1 frozen-fleet rule and needs the
  owner's explicit approval at 2A Gate 0.

## 6. Escalation

| Failure class                                         | Detected by                                 | Next move                                                                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lint or type errors only                              | Check output                                | **Repair round:** same model, same session (resume) or same worktree, fed the exact errors. Max 2 rounds. The error count must drop, otherwise treat as logic. |
| Logic wrong                                           | Tests fail                                  | **Fresh run, one rung up:** higher effort, then a higher tier. Fresh means a clean worktree plus a short failure summary.                                      |
| Spec or scope problem, or two lanes fail the same way | Scope check, same failing test in two lanes | **Back to the Architect.** Re-split the task. Record a decomposition miss with its task class.                                                                 |
| Ladder exhausted or budget hit                        | Counters                                    | Back to the Architect, or a human gate.                                                                                                                        |

Workers run their own checks (tests, ruff/eslint, typecheck) before they finish.
Harness repair rounds are the safety net. A repair round belongs to the same
rollout, so the ledger separates "first-try pass" from "pass after repair".

**Anti-gaming checks** fail a run that adds `noqa`, `type: ignore` or test skips,
deletes assertions, loosens lint or test config, or edits files outside its
allow-list (tests written by the Architect are outside it).

## 7. Parallel work

- **Throughput (main mode):** different tasks with disjoint allow-lists run at
  the same time in separate worktrees, on different lanes.
- **Exploration (side budget):** the same task on 2–3 lanes, only to learn which
  pairing wins for that task class. A bandit router explores where data is thin
  and exploits where it is strong. Exploration uses quota near the end of a
  window that would otherwise expire.
- **Default is serial and cheap.** Up to 3 economy attempts per task when time
  allows.

## 8. Data

**Committed per project:** `docs/missions/ledger.jsonl`, one summary row per run.
Full transcripts stay local in `.tasks/logs/` and are never committed.

Each row: mission, feature, task, run id, parent run, group id, attempt, repair
round; CLI and version, door, pool, billing class; requested, resolved and
observed model; effort; fast state; task class tags; allow-list size; task text
tokens; STE flag; active lesson ids; experiment id; wall time; turns; tool calls;
input, output, cache and reasoning tokens; cost (reported or estimated, with its
source); quota share of the window (estimated); per-check results with counts;
diff size; scope and anti-gaming flags; failure class; escalation reason.

Every number carries a source flag: `observed`, `estimated` or `unknown`.

**Upstream (purrfect-harness):** distilled lessons only, through `skillify`.
Raw data never leaves the project.

**Derived views (never stored):** progress (accepted / total, weighted by size),
burn-up with an ETA, tokens and quota per accepted feature, first-try rate,
repair rate, decomposition-miss rate, pass rate per lane × task class with
counts, lesson effect before and after.

## 9. Board

A static HTML file regenerated after every run event, opened from disk, with
`<meta http-equiv="refresh">` every 15 seconds. No server. Tailwind v4 browser
build, out-of-the-box styling. It shows the mission map, side-by-side rollouts
(steps from each CLI's JSON events), the ladder, quota per pool, the lane ×
task-class matrix, the benchmark trend, lessons and the next gate. Gate actions
are commands with a copy button; the board never runs commands. A mock exists:
[https://claude.ai/artifact/EyfmKPhPL2ohdnCib8yeW2](https://claude.ai/artifact/EyfmKPhPL2ohdnCib8yeW2) (private, example data).
Gates also send a macOS notification.

## 10. Benchmark

Two held-out sets per project, run every 2–4 weeks and on every harness release.

- **Task set (10–20 tasks):** measures lanes and task writing.
- **Mission set (2–3 goals):** measures the Architect's splitting.

Selection criteria: graded by scripts only; harvested from real accepted work
(parent commit + its tests, the accepted diff proves it is solvable);
representative of the project's task classes; calibrated so cheap lanes pass
20–80% in a pilot; discriminating between lanes; hermetic (pinned commit and
lockfile, no network, no secrets, flaky tasks dropped after 3 pilot runs);
never quoted in a lesson or skill; about 15 minutes or less per task on an
economy lane; versioned (v1 never edited) with a stable core.

Protocol: 2 runs per task and lane. Baseline: Sol at high effort, alone. Report:
pass rate, tokens per pass, quota per pass, wall time, change since last run.

## 11. Learning and outside findings

- Lessons come from ledger patterns (for example "auth tasks across 3+ files
  fail on economy, split by layer"). The Architect reads a short distilled guide
  at planning time.
- Each lesson has an id. Runs record the active lesson ids, so the effect of each
  lesson is measured.
- Outside findings enter as: source, claim, change, metric, trial size, adopt
  rule, status (`proposed → trial → adopted | rejected`). Rejected ideas keep
  their data.
- **X-003 (trial):** write task text in about 80% ASD-STE100. The owner also
  wants all harness files in about 80% STE; that rewrite runs as part of X-003
  so its effect is measured.
- **X-FAST (deferred):** fast modes on, against off. Entry: about 30 accepted
  features with fast off, about 10 runs per lane in 3 or more task classes, and 2
  benchmark cycles. Metric: accepted features per hour against features per
  quota share (and $ where billed).

## 12. Where it runs

Missions run on the owner's Mac, where the CLIs are logged in: the Claude Desktop
app, or `claude remote-control` in the repository folder, so the owner can drive
from the Claude app. Harness development (code, tests, PRs, releases) can run in
cloud sessions. Subscription logins never go into a cloud environment.
