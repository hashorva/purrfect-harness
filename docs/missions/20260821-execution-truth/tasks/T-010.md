## Objective

Replace receipt-presence inference with one exact Phase 1 evidence chain:

`ExecutionSpec -> ExecutionReceipt -> VerificationRecord -> features.json acceptance`

Verification must target a caller-supplied UUID `run_id`, load that run's strict worker
receipt and exact spec bytes, run the checks authorized by the committed worker task,
and atomically publish one immutable VerificationRecord. A separate orchestrator-only
acceptance entry point may then change exactly one feature from `passes: false` to
`passes: true` while recording the accepted run and exact verification-record hash.

Decisions are fixed:

- Keep ExecutionSpec v2 and ExecutionReceipt v1 unchanged. The verification commands
  are authorized by the binding task bytes at `receipt.git_before.head`: load the task
  with Git from that exact base commit, hash those bytes, and parse only the strict
  `## Verification commands` JSON-argv bullets used below. Never read commands from a
  mutable working-tree task and never execute an implicit shell string.
- `scripts/verification_record.py` is the dependency-free shared policy/validator.
  `scripts/verify-mission.sh --run-id <uuid> [mission-dir]` is the real verification
  entry point. `scripts/accept-feature.sh --run-id <uuid> --verification-sha256 <hex>
  --accepted-by <identity> [mission-dir]` is the distinct acceptance entry point.
- A run is verifiable only when its exact strict receipt is a completed, exit-zero,
  in-scope worker attempt for the exact mission/task/feature/work-unit/attempt; its
  `workspace_changed` is true; and the current Git-visible repository snapshot exactly
  equals the receipt's `git_after` before and after all authorized checks.
- Store records at
  `docs/missions/<slug>/verification/<run_id>.json`, using canonical JSON, atomic
  no-clobber creation, a read-only final file, and parent-directory fsync. Link exact
  spec, receipt, and committed task paths plus SHA-256 hashes. Record each command's
  argv, start/finish time, exit code, and stdout/stderr SHA-256 without copying arbitrary
  output. The record contains verification result only—no acceptance fields.
- Identity/binding failures create no record. Once exact identity is established,
  execute every authorized check; publish a `pass` or `fail` record and return nonzero
  for failure. A run has at most one record and cannot be re-verified or overwritten.
- Acceptance validates the exact canonical record bytes/hash, requires `result: pass`,
  revalidates all mission/feature/run/spec/receipt/task links, and refuses while any
  dispatch workspace lock exists or `PURRFECT_DISPATCH_LOCK_PATH` is set. It atomically
  changes only the matching feature, preserving all prior fields and adding exactly
  `accepted_run_id`, `accepted_verification_sha256`, `accepted_at`, and `accepted_by`.
  This is procedural authority within a same-user local repository, not a security
  boundary against a malicious process with equivalent filesystem credentials.
- Mission-wide `verify-mission.sh [mission-dir]` audits acceptance rather than inferring
  it from receipts: every non-bootstrap `passes: true` feature must name one exact
  passing VerificationRecord and matching hash. `--require-workers` requires accepted,
  verified worker evidence; an unrelated successful receipt cannot satisfy it.
- Preserve historical strict receipt validation and brain evidence checks where they
  remain relevant. Remove timestamp, suffix, untagged, latest-success, and feature-state
  heuristics as authorization for a run.
- Do not add `acceptance.json`, a mutable lifecycle artifact, AWUs, learning, analytics,
  dashboards, LangGraph, ACP migration, adaptive routing, or cross-repository dispatch.
- F005 remains `passes: false` in the worker result. Only the orchestrator may invoke
  acceptance after independently reviewing the implementation and negative evidence.
