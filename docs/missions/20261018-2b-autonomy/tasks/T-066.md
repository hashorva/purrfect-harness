## Objective

The loop runs with no Claude session open: `nohup bash scripts/mission-run.sh <mission> --provider codex > .tasks/mission-run.out 2>&1 &`, or the same command inside `tmux new -d`. Every step completes by process exit; nothing polls, sleeps or watches; routine steps are rules in the script and wake no model. It is a thin chain of at most 70 lines.

1. New `scripts/mission-run.sh` (`set -euo pipefail`; bash 3.2 compatible, so no `mapfile`; run from the repo root):
   - Usage `mission-run.sh <mission-dir> --provider NAME [--feature F0xx]`. A missing provider, an unknown argument or a mission without `features.json` prints the usage to stderr and exits 2.
   - The steps are arrays read with `read -r -a` from `MISSION_RUN_WORKER`, `MISSION_RUN_VERIFY` and `MISSION_RUN_REVIEW`, defaulting to `bash <scripts dir>/spawn-worker.sh`, `bash <scripts dir>/verify-mission.sh` and `bash <scripts dir>/spawn-brain.sh` (the dry run swaps in stubs). Each step runs with stdin from `/dev/null`.
   - `event` appends one line to `.tasks/events.jsonl` with `jq -cn … '$ARGS.named'`, always with `at` (`date -u +%Y-%m-%dT%H:%M:%SZ`) and `feature`. `stop EVENT DETAIL CODE` appends `{event, detail}`, prints `mission-run: EVENT: DETAIL` and exits with CODE.
   - Plan rules, in one embedded `python3 -` block that prints the feature, the gate (or `-`) and the open task paths on one line:
     - The feature is `--feature`, or else the first `run_order` id whose `passes` is not `true`. If none is left: `stop done "every feature passes" 0`.
     - The tasks are the `<mission>/tasks/T-*.md` files whose front matter (between the first two `---` lines; the body does not count) says `feature: <id>`, sorted by their numbers (`T-003` before `T-003-R1`).
     - A family (a task and its `-R<k>` retries) is done once any member has a record in `<mission>/verification/*.json` with `result` `pass`. Otherwise only its newest member runs.
     - The gate is `GATE <n>` when the feature is listed in that gate's `Held after` sentence (`F001 and F002`; ranges like `F008–F012` are expanded) and every other listed feature passes.
   - Per task, rounds 1 to `MAX_ROUNDS=2`:
     - Remember the event line count and run the worker step with `<task> --provider P --feature F --attempt <round>`. The run id comes from the newest worker `run_exit` after that line. If there is none: `stop blocker "<id>: no worker run started" 4`.
     - Run the verify step with `--run-id <run> <mission>` (exit 0 is `pass`, anything else `fail`). Commit `<mission>` if it changed (`docs: <id> verified (<result>)`), then append `{event: verify, task, run_id, round, result}`.
     - On `pass`, run the review step with `<mission> review`. Its verdict is the output of `python3 <scripts dir>/validate_verdict.py --receipt <receipt of the newest brain run_exit>`; if that fails: `stop blocker "<id>: review gave no valid verdict" 4`. Commit `<mission>` if it changed (`docs: <id> review round <round> (<verdict>)`) and append `{event: review, task, run_id, round, verdict}`. `PASS` moves on to the next task.
     - After the last round without a pass: `stop decision_needed "<id>: 2 rounds without a pass; split it (F006)" 3`.
   - After the last task: `stop gate_reached "GATE <n>" 0` when there is a gate, else `stop decision_needed "<feature>: every task passed; accept it" 3` (only the orchestrator accepts a feature).
   - A header comment of at most 4 lines gives the usage, the nohup and tmux forms, the exit codes and the three override variables.
2. `scripts/validate_verdict.py`: a new mode `--receipt <receipt.json>`, placed before the final usage branch. It reads the receipt and takes `final_answer(receipt["provider"], <bytes of receipt["log_path"]>)`, importing `final_answer` from `observe_output` inside the branch. It applies `extract_last_json_object` to that answer (a missing answer counts as `""`) and validates the result against `schemas/review-verdict.schema.json` next to the scripts directory (`REGISTRY_PATH.parent`). Any `OSError`, `ValueError`, `KeyError`, `TypeError`, `RecursionError` or schema error goes through `report_schema_error` and returns 1. On success it prints the `verdict` value (`PASS` or `FAIL`) and returns 0. The other modes do not change.
3. `harness-manifest.json`: `scripts/mission-run.sh` goes right after `scripts/verify-mission.sh` in both `install_payload_paths` and `update_paths`.
4. New `tests/test-mission-run.py` (unittest; `tests/run-tests.sh` discovers it).
   - One Python stub, `stub.py <step> <args…>`, serves all three steps. It appends `<step> <basename of the task (worker) or of the last argument>` to `calls.txt`, pops its result from `<step>.queue` and leaves what the real step leaves:
     - Worker: a `run_exit` line with role `worker` and a new UUID (the result `none` writes no line).
     - Verify: a record `{"work_unit": "x", "result": <result>}` at `<mission>/verification/<run id>.json`; exit 0 only for `pass`.
     - Review: it fails when `git status --porcelain` is not empty. It writes `<mission>/PROGRESS.md`; a log holding a claude `result` event whose text is a schema-valid verdict with the queued value; a receipt `{"provider": "claude", "log_path": <absolute log>}` under `.tasks/`; and a `run_exit` line with role `brain` that names that receipt.
   - A helper builds a fresh Git repo for each run. Its mission `docs/missions/m` has:
     - `GOAL.md`: `- **GATE 1 — Fixture.** Held after F001 and F002. Text.`
     - `run_order` `["F001", "F002"]`; F002 does not pass, and F001 passes unless the case says otherwise.
     - Tasks `T-001`, `T-002`, `T-003` and `T-003-R1` (feature F002) and `T-004` (feature F001), each with the body line `feature: F002`.
     - Records: `T-001` pass and `T-002` fail.
     - A `.gitignore` for `.tasks/`, `calls.txt`, `*.queue` and `stub.py`.
   - The helper runs `nohup bash <repo>/scripts/mission-run.sh docs/missions/m --provider codex` with stdin closed and every `CLAUDE*` and `PURRFECT_*` variable removed.
   - `test_rounds_skip_done_families_and_stop_at_the_gate`:
     - Queues: worker `w w w`, verify `fail pass pass`, review `PASS PASS`.
     - Exit 0.
     - The non-`run_exit` events are exactly `verify T-002 1 fail`, `verify T-002 2 pass`, `review T-002 2 PASS`, `verify T-003-R1 1 pass`, `review T-003-R1 1 PASS`, `gate_reached GATE 1`.
     - The calls are `worker T-002.md`, `verify m`, `worker T-002.md`, `verify m`, `review review`, `worker T-003-R1.md`, `verify m`, `review review`.

## Why each check exists

- The oracle fails on the base: `validate_verdict.py` has no `--receipt` mode, so it reads `--receipt` as a schema path. It passes only when all of these hold:
  - a review receipt yields `FAIL` from the final answer in its log;
  - an invalid verdict is refused with exit 1;
  - the manifest ships `scripts/mission-run.sh` on install and update;
  - the script refuses a call without `--provider` with exit 2.
  Its files live in a temporary directory.
- `tests/test-mission-run.py` is the dry run. Its stub steps come in through the override variables and run under `nohup` with no Claude session. It proves the rounds, the round limit, skipped done families, the newest retry, front-matter-only feature matching, gate detection, the decision and blocker stops, the commits that keep the tree clean for the next step, and the step events.
- `tests/test-verdict.py` keeps the other validator modes unchanged.
- The size and word check keeps the script a thin chain (at most 70 lines) that never sleeps, watches or starts a model CLI itself.
- Manifest JSON validation, shellcheck, the full suite (its install and update fixtures copy the manifest payload), clean tree, no `__pycache__`: standing checks.
