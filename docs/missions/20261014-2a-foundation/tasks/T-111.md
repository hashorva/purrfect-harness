## Diagnosis (planner, from reading the code; confirm it, do not trust it)

Each race puts process start-up or a live-tree read inside a wall-clock window:

- **R1:** `test_stall_watchdog_stops_silent_providers_for_worker_and_brain`, subtest "ticking worker completes".
  - The stall and idle limits are both 0.3 s.
  - The runner's clock starts at `Popen` (`execution_runner.py:376`), so the stub's python3 cold start, its spec glob, and the `invoked.json` write must all finish within 0.3 s.
  - Under load the run ends `stalled` (rc 123).
- **R2:** `test_runner_and_wrappers_refuse_negative_and_non_finite_timing_values`, valid value `"0.25"`.
  - `SPAWN_WORKER_TIMEOUT_SECS=0.25` must cover the stub's start-up.
  - Under load the run ends `timed_out` (rc 124).
- **R3:** `test_workspace_lock_spans_provider_and_receipt_then_releases`.
  - The polling caps (`time.time() + 5`, twice) and the `communicate(timeout=5)` calls must cover about 15 python3 start-ups in the `spawn-worker.sh` preflight, plus the TERM/KILL chain.
- **R4:** `tests/run-tests.sh:128` `cp -R "$HARNESS/." "$RELEASE_FIXTURE"` copies the live `.tasks/` and `.git/`.
  - Concurrent Opus processes create and delete files there (logs, atomic temp files, `index.lock`).
  - A vanished or locked file makes `cp` fail, and `set -e` then aborts the suite.

`tests/test-seat-smoke.py` has no wall-clock assertion and copies only `scripts/` and `schemas/`, so it is out of scope. The `git gc` race is already fixed (`gc.auto 0`, line 131).

## Why each check exists

- **Command 1, the oracle (deterministic, not probabilistic).** A `python3` wrapper that sleeps 0.6 s before starting the real interpreter reproduces the mechanism behind the load failures: interpreter cold start inside a timed window.
  - On base it fails every time: R1 is stalled (0.6 > 0.3), R2 is timed out (0.6 > 0.25), and R3's preflight of about 15 python3 starts takes about 9 s, more than 5.
  - The sleep is a lower bound, so no scheduler luck is involved.
- **Command 2 (deterministic).** It extracts `copy_harness_tree` and runs it on a tree whose `.tasks/logs` and `.git` cannot be read, standing in for files that concurrent writers lock or delete.
  - On base it fails because the function does not exist. A `cp -R` of everything also fails, on the permission error.
  - It also proves that dotfiles and symlinks are still copied.
- **Command 3, the requested stress check.** It runs the three methods 5 times while 4 busy-loop processes load the CPU, and requires 5/5.
  - It is not the oracle: real load cannot be guaranteed to make base fail. The deterministic assertions that prove the races are commands 1 and 2.
- **Commands 4–6:** the three methods without load.
- **shellcheck, the full suite, clean tree, no `__pycache__`:** standing checks.
