Today a second `verify` of a run is refused, so an environment failure (T-004) can never be
re-verified. Allow numbered records; keep every record immutable.

1. Record names: the first record of a run stays `verification/<run_id>.json`; later records are
   `verification/<run_id>.<n>.json`, n = 2, 3, ... (next free number, created with the existing
   no-clobber `atomic_create`). Record content is unchanged (schema v1).
2. `accept`: find the run's records (`<run_id>.json` and `<run_id>.<n>.json`); exactly one must
   have the cited sha256, and it must be `pass`; then the existing checks.
3. `audit`: the accepted hash must match one record of the accepted run; the run's record
   numbers must be contiguous from 1 (a gap is an audit failure).
4. `docs/missions/ORCHESTRATION.md`: one or two sentences: a run may be verified again; each
   verification adds a numbered immutable record; acceptance cites the record hash; failed
   records stay as history.
5. Tests (temporary repositories): verify the same run twice and get `<run_id>.json` and
   `<run_id>.2.json` with the first byte-identical afterwards; accept by the second (pass) hash;
   accept by a fail record's hash is refused; a hash that matches no record is refused; a
   missing `<run_id>.2.json` while `.3.json` exists fails the audit; the existing single-record
   flow passes unchanged.
