# Making rule 6 cheap (Architect, run a6f4e954-7bc6-4100-8a1a-06d09edd4d21)

Yes: promote `.tasks/rule6.py` to a committed `scripts/check-task-oracle.py`,
built as one S task with its own oracle. The test fixture is a task whose oracle
already passes on the base, and the tool must exit 1 on it. Today's script exits
0 in that case: it only fails when a command fails after the patch, so a
non-discriminating oracle passes the check. That is the same class of defect as
T-037's "exit-code check that passed on the base". Five changes make the tool
cheap to run and hard to get wrong:

1. Parse the verification bullets with the verifier's own parser (import it),
   not a second regex, so the task writer and the verifier cannot disagree.
2. Let a task mark each command `oracle` or `regression`. Oracle commands must
   fail on the base and pass after. Regression commands (shellcheck, the suite,
   clean tree, bytecode) only need to pass after. On the base, run regression
   commands only when `--full` is given; the baseline is already known green.
3. Exit 1 unless there is at least one discriminating oracle and nothing fails
   after the patch.
4. Keep the reference patch in `.tasks/reference/<task>.patch`, outside the
   tree, and write a JSON result (base rc, after rc and duration per command,
   patch sha256, base commit). The Front Desk links that result from an
   `oracle` progress event.
5. Cache results by (base commit, task sha, patch sha) so a re-check after a
   task-text-only edit is free. Keep the scratch clone, not a worktree, so the
   live `.git` is never touched.
